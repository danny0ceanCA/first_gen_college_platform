# Coordinator password setup and first sign-in

The admin dashboard shows **Approvals → Coordinators → Approved → Account setup & sign-in**. Each record has a password milestone and its earliest recorded successful Origen sign-in, with timestamps in the administrator's local time zone. Refresh status reloads this evidence independently of coordinator activity statistics. Directory refresh also refreshes both panels.

## Evidence and limitations

Only an Auth0 `scp` (successful password change) records password setup. `scpr` (reset requested), `ss` (signup, including operator-created users), emails, email verification, failed logins, and client-side claims never complete that milestone. `s` records a successful sign-in only when `client_id` matches the configured Origen application allowlist. Post-login Actions are not used as proof because they execute before a login finishes.

“Not yet recorded” is deliberately not a claim that an existing coordinator has never set a password or used their account. Social sign-ins do not prove a database password exists. The first sign-in is the earliest available confirmed event, including any operator history replay. Auth0 retention may prevent recovering the true first login for old accounts. The UI discloses this limit and the date tracking started.

The webhook stores only subject, earliest password timestamp, and earliest sign-in timestamp for known institution representatives. Unrelated/student-only identities are discarded. No raw Auth0 logs, emails, IP addresses, tokens, password values or student conversations are retained. Later resets never overwrite the original password milestone. Duplicate, concurrent, or out-of-order delivery preserves the minimum timestamp. Deleting the representative cascades these records; late events cannot restore a closed or erased identity.

## Release and Auth0 configuration

1. Apply migration `083_coordinator_activation.sql` using the separate migration credential. Run `npm run db:grant-runtime` using the existing provisioning workflow. The runtime receives execute permission on two narrow functions, with no raw access to either new table. Maintenance receives no new table privileges.
2. Configure the API's `AUTH0_COORDINATOR_EVENTS_SECRET` as a fresh 32-byte base64url secret (43 characters). Keep it in the deployment secret store and Auth0 stream authorization only. Configure `AUTH0_COORDINATOR_CLIENT_IDS` as the comma-separated allowlist of Origen web/mobile Auth0 application IDs. Neither value belongs in frontend configuration. Existing production configuration rejects a partial or weak setup; startup checks the migration and function privileges when enabled.
3. Deploy the API and frontend. Create a dedicated Auth0 **Custom Webhook** log stream for this tenant pointing to `https://<API host>/api/auth0/coordinator-events`. Set the HTTP Authorization value to `Bearer <secret>`, Content Type to `application/json`, and Content Format to `JSONARRAY`. The receiver also accepts JSON lines and a single log envelope. Preserve existing streams. Select **Login - Success** and **User/Behavioral - Success** in the stream's category filters; the latter includes successful password changes as well as reset requests, which the receiver deliberately ignores. The receiver always filters the exact event codes and login client IDs itself. See [Auth0's filter reference](https://auth0.com/docs/customize/log-streams/event-filters).
4. The endpoint returns 200 only after the whole batch commits. Invalid authorization returns 401; a failed database write returns 503 for provider retry. Verify stream health and a synthetic successful password reset/login. Do not use a real coordinator's password or consume their invitation to test this feature. The route never changes password state or authentication/approval requirements.
5. Replay retained history with `node scripts/sync-coordinator-activation.mjs` in an operator environment containing `MIGRATION_DATABASE_URL`, `AUTH0_DOMAIN`, `AUTH0_COORDINATOR_CLIENT_IDS`, and optionally `AUTH0_CLI_BIN`. The Auth0 CLI session needs `read:logs`. The script checks known coordinator identities only, projects minimum fields, applies the same filters, and prints counts only. It needs no persistent Management API token in the web service. History replay is safe to repeat and can recover a signup/login that arrived before an applicant became a known representative. Run it after rollout and when investigating missing older milestones.

Auth0 custom webhook delivery is asynchronous. A user may need to refresh after a short delay. The history disclosure shows the last received event batch; it is not a claim that the stream is healthy indefinitely. Disabling the secret/client configuration stops ingestion and shows an explicit live-tracking-disabled message while preserving previously confirmed milestones. Monitor Auth0 stream health and replay retained events after an outage; retention means recovery is not unlimited.

## Verification

`server/coordinator-activation.test.mjs` checks provider payload parsing, successful events versus requests/failures/signup, application filtering, body bounds, shared-secret authorization, browser scope rejection, whole-batch failure, and safe history replay. Its disposable PostgreSQL tests apply all migrations and real restricted runtime grants, then cover concurrent/out-of-order updates, first-event preservation, permission gates, raw-table denial, closed identities and cascade erasure. Existing approved-directory, staff-access, and gateway tests remain required. Browser review covers pending/completed/error/disabled states and coordinator switching at desktop and mobile widths.
