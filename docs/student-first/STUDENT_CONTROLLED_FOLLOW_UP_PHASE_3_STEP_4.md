# Phase 3, step 4 — Follow-up conversations and private updates

Implemented locally. The backend capability remains **default-off**. This step connects the existing voice-and-binder experience; coordinator sharing stays a separate step 5 decision. No production migration, deployment, provider call or feature enablement was performed.

## Student experience

Live and Realtime advertise the same application delivery protocol and use the same server-selected optional check-in. The first question is spoken exactly once, without an additional generic greeting. A current student question, interruption, provider/guide handoff, scope change or continuation does not create another opening allowance. A completed question consumes the one-time check-in without implying that the student answered, understood, acted or succeeded.

The student can request a check-in or reschedule it by voice. The server compares the independently captured utterance to the accepted action title or the immediate answer to the current delivered check-in. Ambiguous targets require clarification; the voice action list is bounded to 20 choices. The server derives the date from the utterance, supporting next time, tomorrow in the device time zone, ISO calendar dates and full English/Spanish month/day/year dates. Unsupported or ambiguous dates, including “next week” or a weekday without a full calendar date, require a concrete date or binder choice. Neither a coordinator date nor a personal action deadline supplies follow-up consent.

Origen reads the action, chosen date, time zone and one-time/private scope before saving. The student explicitly approves in the immediately following turn, for example “Yes, save it” or “Sí, guárdalo.” A bare yes is insufficient. An unambiguous cancellation is processed directly from the captured speech without waiting for a model tool or asking again. “Not now” uses the opening's independent-turn receipt to pause that check-in. Neither cancellation nor a decline changes task progress or notifies a coordinator. Replaying an old cancellation cannot stop a newly approved check-in.

When the student asks to record what happened, Origen proposes a private update. The readback separates the reported action, reported outcome, optional detail/helpfulness/event date, student-reported provenance and any separately requested canonical task-status change. “I called the office” can accompany a completed contact action and a pending outcome. The report does not establish insurance eligibility, waiver approval or causation. Ordinary conversation, silence, a model summary and coordinator advice do not create structured reports.

**My private updates** appears within the existing accepted action. Students can write, review, correct and delete their own updates. The controls distinguish event date from recorded date, leave helpfulness unrecorded by default and keep task progress unchanged unless explicitly selected. Saving, correcting and deleting show server-confirmed state. Lost responses direct the student to check saved updates rather than automatically submit again. Offline/privacy changes clear previews. There is no chat UI, caption stream, outbound reminder or coordinator layout change.

## Evidence and lifecycle

- `ProfileVoice.tsx` connects both adapters to `followUpOpeningPlayback` and `followUpVoiceTools`. `voiceMemoryTools.evidence()` supplies the registered turn; model arguments cannot provide ownership, approval, capture sequence or playback evidence.
- The next independent turn waits for pending presentation receipts. The app requires matching response creation, complete generation, complete text, audible output and drained playback. Interruptions, muting, forced flushes, failed output and stale sessions cannot approve a proposal. Live additionally requires observed output samples; an idle stream and generated transcript alone are insufficient.
- `/api/student-follow-up-report` provides strict binder load/prepare/confirm contracts. `/api/student-follow-up-voice` provides strict independently captured voice operations. Internal selection, binding and consent flags are not exposed as model tools.
- Migration `107_student_follow_up_conversations.sql` adds owner-scoped proposals and content-free cancellation receipts. Reports use the existing private report store; task changes use the canonical plan/step rows. Report and approved task change commit atomically. Proposal payloads are removed after commit; receipts do not retain report wording. Only current report versions are exported or displayed. Corrections replace the record; stale approvals cannot restore edited/deleted reports.
- Source/permission/action versions are checked again at approval. Source and permission changes permanently invalidate pending proposals, including a later restoration of access. Source locks precede proposal locks. Report changes invalidate live memory revisions. The existing source guard also protects voice readbacks. Student/action/account deletion follows existing cascading ownership; restore discards proposals and cancellation capabilities and keeps the existing conservative report fences.
- The new tables are restricted from runtime raw access and all coordinator projections. Runtime receives only the scoped command. There is no write to coordinator requests, notifications, outboxes, ordinary notes, model extraction, general progress/helpfulness reports or recommendation training from a private report. An explicitly approved plan-status change remains a separate canonical task fact.

Voice writes honor both `ORIGEN_STUDENT_FOLLOW_UP` and the existing live-write capability. Cancellation remains possible during a pause, and students retain access to their saved reports and deletion controls. Readiness requires migrations 104–107 and four scoped command grants. The release verifier includes the new database/controller suites and bilingual private-update browser journeys. No new database, Redis instance, scheduler or paid service is required.
