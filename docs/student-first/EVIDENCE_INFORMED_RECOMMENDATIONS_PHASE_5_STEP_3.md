# Phase 5, step 3 — Explainable recommendation selection

Implemented locally on November 2, 2026, on `codex/evidence-informed-recommendations`. This adds deterministic eligibility and ordering, an account-scoped input resolver, transient freshness receipts, bilingual explanations and a synthetic comparison with `binder-next-step-v1`. Both recommendation flags remain false by default. Student-facing voice/binder delivery and acceptance are step 4; permissioned recommendation evaluation is step 5.

## Decision behavior

`server/recommendation-policy.mjs` exports a pure `decideRecommendation` function under policy `evidence-informed-v1`. The same authorized input and evaluation time produce the same decision. It returns at most one candidate, a focused clarification, no applicable candidate, or an unavailable result. Lookup failure does not mean help does not exist. Missing goal/process produces a question; materially different equally suitable actions require clarification rather than an arbitrary choice.

Eligibility precedes ordering. The policy checks student and organization scope, exact source version, publication/review freshness, explicit private-source focus, goal/process, campus/term, prerequisites, conflicting evidence and existing action state. Completed, archived, deferred, declined, already accepted elsewhere and changed-goal entries are excluded. Exact normalized English or Spanish wording already present in a canonical action suppresses a duplicate template. This is duplicate prevention, never a semantic link between advice and an outcome. Conflicts in applicable evidence cannot be offset by a different eligible candidate or higher ranking.

Among eligible candidates the documented ordering is existing accepted work, coordinator advice, then reviewed templates; within that ordering it considers satisfied prerequisites and verified future date constraints. Exact equivalent wording uses stable source IDs to avoid churn; materially different ties ask a question. The current resolver revisits only an explicitly selected private action or response, so it does not classify or rank all free-form private actions against a catalog. Those source preferences define the policy without inventing goal/process metadata for existing private text. There are no learned weights, coordinator popularity scores, demographic features or predicted success rates.

Personal target dates apply only to accepted actions and use the requested local time zone. An unknown or passed personal date adds no urgency and implies no failure. Official deadline priority requires fresh, exact official applicability support; a passed verified submission deadline excludes that submission instruction. No deadline is extracted from prose. Practical preference support currently consists of explicit focus and local time zone; channel, cost and other preferences have no structured catalog fields yet and are not inferred.

The explanation identifies a reviewed general question, an existing accepted action, or the student's named coordinator suggestion. English and Spanish labels preserve the full original private wording without invented translation or clipped conditions. Template, source and coordinator wording remains untrusted reference data. The model may explain the decision and its limits; it cannot rerank alternatives, fill missing facts, claim insurance eligibility or award amounts, save an action, schedule follow-up, share information or grant evaluation permission.

## Authorized input and freshness

`server/recommendation-selection.mjs` exposes internal selector/verifier functions, not HTTP routes or model tools. The request identifies a student, expressed goal/process, language, time zone, intent and optional exact source/outcome episode references. It accepts no caller-supplied fact booleans, eligibility proof, candidate list or sensitive ranking fields. A separate server-owned current interaction must match the request and confirm an explicit student request. Changed priority, decline, deferral, reconnect, onboarding, scope restart and unrelated binder focus suppress selection. This check is repeated after loading. The existing opening selector and reservation behavior remain unchanged; selection creates no new opening allowance.

Migration `116_recommendation_selection.sql` adds one scoped `SECURITY DEFINER` read function with fixed search path and denied PUBLIC execution. It uses current authenticated account/student eligibility and re-resolves exact private sources and current library publications. Runtime receives only function execution. Startup readiness checks the migration and isolation. Refresh runtime grants with the migration; no new table or recommendation writer is added.

The resolver reads a bounded snapshot twice in a guarded account transaction. Changes to considered publications, source revisions, permission, explicit evidence or duplicate actions invalidate the result, including a competing publication that could change the winner. The transient receipt includes policy, request, input and decision digests and expires within 60 seconds or the source expiry, whichever comes first. Before later delivery, the verifier reselects from current authorized sources and checks the same decision. A receipt grants no acceptance or consent. Feature pauses, changed intent, publication withdrawal and privacy restore invalidate use. No decision, exposure, student preference or evaluation record is retained, and private content is not written to operational logs.

Fixed budgets are 50 candidate templates, 50 existing actions for duplicate checks, eight explicitly referenced outcome episodes, 100 evidence rows, 120 KB per input snapshot, two top-level snapshot reads, three seconds per SQL statement and four seconds for the whole request, including pool acquisition. Nested source guards run within the statement budget. Overflow is unavailable; the policy never ranks a silently truncated set. An aborted/timed-out request returns no candidate, and any acquired connection is released after its bounded operation unwinds.

## What evidence can establish today

Only exact, current, student-approved private outcome episodes for the selected accepted action can contribute structured facts. Existing outcome permission, account scope, action relationship, source and report versions are rechecked. Shared coordinator observations are not imported. Different declared episode scopes/windows, disputed evidence and contradictory supported claims require clarification.

A student report of document submission can establish **reported submission**. A report that a decision was received can exclude a pending-decision action. A pending report is usable for seven days from recording; age only removes its use and never proves completion. These facts do not establish document acceptance, eligibility, insurance approval, requested document format or institutional verification. Current structured evidence does not establish `document_requested` or `document_prepared`, so the resolver asks for those prerequisites rather than deriving them from notes or conversational prose.

The current database has no authoritative confirmed campus/term identity or official applicability receipt producer. Accordingly, the server selects general reviewed questions and explicit private-source revisits only. It withholds campus-specific templates and can ask which campus is relevant. Free-form school names, outcome institution labels, coordinator organizations and matching official URLs cannot substitute for verification. The pure policy checks exact campus/term, source versions and official proof freshness with synthetic fixtures; that is **not live institutional verification**. Step 4 must connect independently captured intent and any supported structured facts; institutional recommendations additionally require a trusted applicability resolver before they can be enabled.
